# DOCX 변환 재현 기준

[`representative.docx`](../examples/samples/docx/representative.docx)는 이 저장소에서 직접 만든
DOCX→HWPX/HWP 회귀 문서입니다. 본문 글자 서식과 색상, 자동 목록, 병합 표,
표 테두리·셀 음영, 그림, 첫 페이지 전용 머리말, 단순 수식을 함께 담았습니다.
외부 파일의 저작권이나 가용성에 의존하지 않도록
`python scripts/build_docx_fidelity_sample.py`로 다시 만들 수 있습니다.

`python -m pytest tests/test_docx_fidelity_sample.py`는 한글 프로그램 없이 두 형식으로
저장한 뒤 다시 열어 텍스트, 표 색상·테두리 참조, 수식 컨트롤을 확인합니다.
검사는 파일 구조의 보존 여부를 확인하며 페이지 배치나 글꼴 렌더링의 시각적
동일성을 판정하지는 않습니다.

| 요소 | 현재 변환 상태 |
| --- | --- |
| 본문 글자 서식·색상, 인라인 그림 | HWPX/HWP 구조 검사 통과 |
| 병합 표, 직접 지정한 테두리·셀 배경색 | HWPX/HWP 구조 검사 통과 |
| 단순 선형 Word 수식 | HWPX/HWP 수식 컨트롤로 변환 |
| 글머리표·십진·로마·영문 번호 | HWPX 누름틀에 표시값과 목록 정의 보존; DOCX로 돌아오면 자동 목록 복원 |
| 첫 페이지 전용 머리말·꼬리말 | HWPX 첫 페이지 고정 글상자로 표시; DOCX의 첫 페이지 전용 영역으로 복원 |
| 현재 페이지 번호 | HWPX 자동 번호와 Word PAGE 필드로 연결 |
| 일반 Word 필드 | HWPX에 표시값·명령 보존; DOCX에서 필드 명령 복원 |
| 각주·미주 | 양쪽의 참조·주석 영역으로 연결; 혼합 서식·그림·표 보존 검사 |
| 변경 추적·콘텐츠 컨트롤 | 변경 수락 후의 보이는 내용으로 변환; 원본 DOCX의 이력·바인딩은 그대로 보존 |
| 지원하지 않는 Word 수식 구조 | 원본 DOCX는 보존하고 파이썬 변환은 오류로 중단 |
| 테마 기반 표 서식 | 직접 지정한 서식 외의 조건부 효과는 손실될 수 있음 |

완전 재현 여부를 주장하려면 구조 검사와 별도로 같은 글꼴 환경에서 DOCX와
변환 결과의 페이지 수, 텍스트 위치, 표 경계, 그림 위치를 비교해야 합니다.

## 양방향 왕복 검증

`python -m pytest tests/test_docx_roundtrip.py`는 다음 계약을 확인합니다.

- DOCX → HWPX → DOCX에서 표 셀의 혼합 글자 서식, 링크, 그림과 중첩 표를 유지합니다.
- 머리말·꼬리말의 혼합 글자 서식과 그림을 유지합니다.
- 문단 간격·들여쓰기·줄 간격·탭 위치와 채움선을 세 번 왕복해도 누적 변경하지 않습니다.
- 기본 Word 표의 왼쪽 정렬, 위쪽 세로 정렬과 기본 셀 여백을 명시적으로 변환합니다.
- 스타일 이름, 빈 작성자, 생성·수정 날짜를 유지합니다.
- 분수·첨자·근호를 양쪽의 수식 구조로 옮기며, 지원하지 않는 Word 수식을 이어 붙여 다른 식으로 만들지 않습니다.
- 그림만 있는 문단의 정렬과 네이티브 HWPX 테두리·여백을 유지합니다.

2026-10-28 로컬 시각 검증은 본문 혼합 글자 서식, 오른쪽 탭과 점 채움선,
음영 표의 혼합 서식·그림·중첩 표, 분수, 머리말 그림·굵은 글자, 기울인 꼬리말을
함께 넣은 Letter 1페이지 샘플로 수행했습니다. 양방향으로 두 번 왕복한 뒤 실제
Microsoft Word와 한컴오피스에서 PDF를 출력하고 144 DPI PNG로 비교했습니다.

| 비교 | 텍스트 / 페이지 수 / 크기 | 픽셀 차이 |
| --- | --- | --- |
| 원본 DOCX와 DOCX → HWPX → DOCX | 일치 | 0% |
| 위 DOCX와 두 번째 왕복 DOCX | 일치 | 0% |
| 초기 HWPX와 HWPX → DOCX → HWPX | 일치 | 0% |
| 위 HWPX와 두 번째 왕복 HWPX | 일치 | 0% |

Word 결과는 Word끼리, HWPX 결과는 한컴끼리 비교한 수치입니다. 서로 다른 조판
엔진의 출력을 같다고 본 것이 아닙니다. 같은 샘플의 Word와 한컴 출력 사이에는
약 3.05%의 변경 픽셀과 PDF 용지 높이 차이가 남습니다. 페이지는 확대·축소하지 않고
RGB 채널 차이 24를 넘는 픽셀의 비율을 측정했으며, 위의 0%는 픽셀 배열 자체도
동일함을 확인했습니다.

이 결과는 이 샘플과 위 테스트의 지원 항목에 한정됩니다. 모든 네이티브 도형과
Word 확장 기능을 포함하는 임의의 문서가 완전히 호환된다는 뜻은 아닙니다.

## 대체 표현의 왕복 계약

`python -m pytest tests/test_docx_effect_mapping.py`는 아래 대체 표현을 검사합니다.

- `HeaderFooter.apply_page_type="FIRST"`를 첫 페이지에만 존재하는 글상자로 저장합니다.
  선과 채우기를 제거하고 용지 기준으로 배치해 본문 줄바꿈에 영향을 주지 않습니다.
  일반 머리말·꼬리말은 첫 페이지에서 숨깁니다. 역변환할 때 글상자의 실제 내용을
  Word 첫 페이지 전용 영역으로 되돌립니다. 그림·혼합 서식과 가로 용지도 검사합니다.
- 목록은 HWPX의 `CLICK_HERE` 누름틀로 번호·글머리표를 표시합니다. 들여쓰기,
  목록용 탭, 같은 스타일 사이의 문단 간격을 계산하며, 번호 시작값과 단계 정의를
  함께 보존합니다. Word로 돌아오면 `numbering.xml`과 `numPr`을 생성하므로
  목록을 추가하거나 삭제할 때 다시 번호가 갱신됩니다. HWPX 안에서 번호 자체를
  자동 갱신하지는 않습니다. 표시 번호를 직접 바꿨다면 역변환에서도 그 문자열을 유지합니다.
- 일반 필드는 누름틀 표시값과 원래 Word 명령을 보존합니다. HWPX에서 Word 명령을
  계산하지는 않으며, 현재 페이지 번호는 별도로 한글의 자동 번호에 연결합니다.
- 한글 재저장은 사용자 정의 필드 매개변수를 제거할 수 있습니다. 따라서 작은 기능
  정의를 누름틀 이름에도 압축해 보관합니다. 원본 문서 전체를 숨겨 넣는 방식이 아닙니다.
  누름틀 이름을 유지해야 이 정보로 복원할 수 있습니다. 같은 run 안으로 필드 경계와
  표시값이 합쳐져도 읽고 수정할 수 있으며, 주변 본문은 건드리지 않습니다.
- 각주·미주는 본문 참조와 별도 Word 파트/HWPX 주석 영역으로 옮깁니다. 주석 파트
  안의 그림 관계, 표, 글자 서식을 보존합니다. 단독 페이지 나눔은 다음 문단이나 표에
  연결하여 새 페이지 위에 불필요한 빈 줄을 만들지 않습니다.
- 콘텐츠 컨트롤과 삽입·이동된 내용은 실제 보이는 글·표로 펼칩니다. 삭제·이동 전
  내용은 수락된 보기에서 제외합니다. 원본 DOCX 저장과 Word 전용 편집은 원본 구조를
  사용하므로, 이 투영 때문에 변경 이력과 바인딩이 원본에서 삭제되지는 않습니다.

2026-10-28 추가 시각 검증은 첫 페이지/일반 머리말·꼬리말, 목록, PAGE·DOCPROPERTY,
각주·미주를 넣은 2페이지 문서를 사용했습니다. 실제 Word와 한글에서 PDF를 출력해
144 DPI로 비교했고, 한글에서 HWPX를 다시 저장한 뒤에도 목록 정의와 Word 필드 명령이
복원됨을 확인했습니다.
다음 표는 참조번호 서식 보존 수정 전의 측정 기록이며, 수정 후 결과는 마지막 절에 있습니다.

| 비교 | 페이지 수 | 페이지 전체를 분모로 한 변경 픽셀 |
| --- | --- | --- |
| 원본 DOCX → 첫 번째 왕복 DOCX, Word 출력끼리 | 2 → 2 | 약 0.170%, 0.105% |
| 첫 번째 → 세 번째 왕복 DOCX, Word 출력끼리 | 2 → 2 | 0%, 0% (픽셀 배열 동일) |
| 초기 → 세 번째 HWPX, 한글 출력끼리 | 2 → 2 | 0%, 0% (픽셀 배열 동일) |

첫 변환의 차이까지 0%라는 뜻은 아닙니다. 이 백분율은 흰 여백을 분모에 포함하므로
내용의 일치율로 해석해서는 안 됩니다. 첫 번째와 세 번째 결과의 일치는 첫 변환에서
바뀐 상태가 반복 유지됨을 의미합니다. 서로 다른 조판 엔진의 동일성도 보장하지 않습니다. 큰 첫 페이지
머리말이 본문 영역까지 차지하는 문서, 복잡한 주석 번호 재시작과 사용자 구분선은
추가 문서별 검증이 필요합니다. 순수 파이썬 HWP 출력은 목록·필드를 표시 문자열로,
첫 페이지 영역을 글상자의 텍스트로 보존하므로 HWPX 경로의 풍부한 서식 복원 계약과
구분해야 합니다. 지원 밖 수식, 주석 범위, 레거시 OLE/도형 등은 여전히 별도 매핑이나
명시적 네이티브 변환기가 필요한 항목입니다.

## 흰 배경을 제외한 차이 원인 재검증

같은 2페이지 샘플을 다시 분석했습니다. 동일한 Word 조판 엔진으로 출력한 원본과
첫 왕복 결과를 비교했으며, 각 페이지는 144 DPI의 1224 × 1584 픽셀입니다.
각 이미지에서 RGB 채널 중 하나라도 245 미만인 픽셀을 표시 영역으로 잡고,
원본과 결과의 표시 영역 **합집합**을 분모로 삼았습니다. 원본에서 사라진 부분과
결과에 새로 생긴 부분을 모두 포함합니다. 변경 판정은 기존과 같이 RGB 채널 차이
24 초과입니다. 이 정의는 배경이 흰색인 이 샘플에 대한 것으로, 유색 배경 문서에는
그대로 일반화하지 않습니다. 표시 영역이 없는 빈 페이지는 이 비율로 평가하지 않습니다.

| 페이지 | 변경 픽셀 | 표시 영역 합집합 | 전체 페이지 기준 차이 | 표시 영역 기준 차이 | 표시 영역 IoU |
| --- | --- | --- | --- | --- | --- |
| 1 | 3,295 | 8,830 | 0.170% | **37.316%** | 69.785% |
| 2 | 2,036 | 6,248 | 0.105% | **32.586%** | 77.753% |

IoU는 표시 픽셀의 교집합을 합집합으로 나눈 값이며 문서 정합률이나 글자 인식률은
아닙니다. 공백을 제외한 추출 문자열은 같았지만 번호의 크기와 글자의 위치가 달랐습니다.
표시 영역 차이는 아래 세 영역에 전부 포함되었으며, 세 영역 바깥의 변경 픽셀은 0개였습니다.

| 영역 | 직접 확인한 변화 | 해당 영역의 변경 픽셀 |
| --- | --- | --- |
| 1페이지 본문 참조번호와 뒤의 필드 표시값 | 참조번호 11.04 → 6.96pt; 뒤의 글자가 왼쪽으로 3.48pt 이동 | 1,042 |
| 1페이지 각주 줄 | 참조번호 11.04 → 6.96pt; 주석 글자가 왼쪽으로 2.28pt 이동 | 2,253 |
| 2페이지 미주 줄 | 참조번호 11.04 → 6.96pt; 주석 글자가 왼쪽으로 1.20pt 이동 | 2,036 |

원인은 현재 `addons/docx/writer.py`로 옮겨진 `_Writer.note()`가 본문 참조번호와 주석 안의 참조번호를
모두 `vertAlign=superscript`로 생성하던 코드였습니다. 이 샘플 원본의 네 참조번호는
본문과 같은 크기였으며, 번호를 작게 바꾼 결과 번호 뒤의 글자가 당겨졌습니다.
수정 전에는 원본 참조번호의 글자 서식이 공통 `Note` 모델에 전달되지 않았습니다.

원인 분리 실험에서는 변환 결과의 임시 DOCX 사본에서 해당 **네 위첨자 설정만** 제거하고
다시 Word로 출력했습니다. 두 페이지 모두 원본과 픽셀 배열이 완전히 같았고 최대 RGB
차이도 0이었습니다. 따라서 이 샘플에서 구분선, 머리말, 목록이나 조판 엔진 차이를
원인으로 들었던 설명은 정정합니다. 확인된 수정 대상은 참조번호 서식의 수입·보존·복원입니다.
정상적으로 위첨자를 쓰는 원본도 있으므로 모든 참조번호를 일반 글자로 바꾸는 방식은
일반 해법이 아닙니다. 위첨자 설정을 일괄 삭제하는 대신 아래의 원본 서식 보존 경로로
변환기를 수정했습니다.

## 참조번호 서식 보존 수정 후 검증

`Note.reference_run_properties`와 `Note.marker_run_properties`에 본문 참조번호와
주석 내부 번호의 서식을 각각 보존합니다. Word의 직접 서식, 문자·문단 스타일과
문서 기본값을 읽어 독립적인 run 속성으로 만들며, 해석 가능한 테마 글꼴은 실제 글꼴
이름으로 기록합니다. 일반 글자·위첨자·아래첨자, 글꼴·크기·색상·강조뿐 아니라
자간과 명시적인 세로 위치도 유지합니다. 새 Word 문서에서 존재하지 않을 수 있는
문자 스타일 ID에 의존하지 않습니다.

HWPX에서는 참조번호의 문자 모양을 연결하고, 원본 Word 속성은 주석 내부의 빈
`CLICK_HERE` 필드에 보관합니다. 필드 이름에도 같은 작은 기능 정의를 보존하므로
한글 재저장으로 사용자 매개변수가 제거되어도 복원할 수 있습니다. 빈 필드는 글자를
출력하지 않으며 Word 복원 전에 공통 주석 내용에서 제거합니다. 원본 Word 서식 정보가
없는 기존 HWP/HWPX 주석의 기본 위첨자 동작은 유지합니다.

실제 수정된 변환기로 DOCX → HWPX → DOCX를 실행해 Word에서 다시 출력했습니다.
원본과 결과의 흰 배경을 제외한 표시 영역 합집합 기준 결과는 다음과 같습니다.

| 샘플 / 경로 | 페이지 수 | 수정 전 변경 픽셀 | 수정 후 변경 픽셀 | 수정 후 표시 영역 차이 | 수정 후 표시 영역 IoU |
| --- | --- | --- | --- | --- | --- |
| 기존 2페이지 샘플 1쪽 | 2 → 2 | 3,295 | 0 | **0%** | 100% |
| 기존 2페이지 샘플 2쪽 | 2 → 2 | 2,036 | 0 | **0%** | 100% |
| 기존 샘플을 세 번 왕복 후 원본과 비교 | 2 → 2 | — | 두 쪽 모두 0 | **0%** | 100% |
| HWPX를 실제 한글에서 재저장한 뒤 DOCX로 복원 | 2 → 2 | — | 두 쪽 모두 0 | **0%** | 100% |
| 초기 HWPX와 세 번째 HWPX, 한글 출력끼리 | 2 → 2 | — | 두 쪽 모두 0 | **0%** | 100% |
| 본문 번호는 위첨자, 각주 안 번호는 일반 글자 | 1 → 1 | — | 0 | **0%** | 100% |
| 본문 번호는 일반 글자, 미주 안 번호는 위첨자 | 1 → 1 | — | 0 | **0%** | 100% |

수정 후의 모든 위 비교에서 임계값을 적용하기 전 RGB 픽셀 배열도 동일했습니다. 공백을 제외한
문자열, PDF에 기록된 글꼴 계열과 글자별 좌표·크기를 함께 비교했으며 최대 글자 위치
차이와 글자 크기 차이는 모두 **0pt**였습니다. 별도 서식 샘플은 상속된 Arial 14pt의
본문 번호와 Courier New 9pt의 주석 번호, 서로 다른 색상·강조·자간·세로 위치를 사용했습니다.
이 수치는 해당 샘플과 경로의 측정 결과입니다.

`python -m pytest tests/test_note_reference_formatting.py tests/test_render_comparison.py`로
참조번호 서식의 독립적인 3회 왕복, 일반/위/아래첨자, 원본 DOCX 무수정 보존,
한글 필드 매개변수 정규화와 흰 여백에 영향을 받지 않는 비교 지표를 검사합니다.

PNG 비교는 다음 명령으로 재현할 수 있습니다. 이미지 로딩에는 Pillow가 필요하며
두 페이지는 같은 DPI와 크기여야 합니다. 이 도구는 크기를 맞추거나 글자 위치를
자동 정렬하여 오차를 숨기지 않습니다. 빈 페이지의 표시 영역 점수는 `null`입니다.

```sh
python scripts/compare_document_renders.py original-page.png returned-page.png --output foreground.json
```

## 확장 서식과 한글 자동 갱신 검증 (2026-10-29)

별도 1페이지 샘플에 테마 글꼴·색상, 글자 간격·세로 위치, inline 콘텐츠 컨트롤,
자르기·회전한 그림, 떠 있는 그림, 조건부 표 스타일·해치 음영, 자동 번호 목록과
첫 페이지 머리말을 넣었습니다. DOCX → HWPX → DOCX를 세 번 반복하고 실제 Word에서
PDF로 출력했습니다. 세 번째 HWPX를 실제 한글에서 재저장한 파일도 DOCX로 복원해
출력했습니다. 모두 144 DPI이며 이미지 확대·축소나 좌표 정렬을 적용하지 않았습니다.

| 비교 경로 | 페이지 수 | 흰 배경 제외 변경 비율 | 표시 영역 IoU | 최대 RGB 채널 차이 |
| --- | --- | --- | --- | --- |
| 원본 Word → 3회 왕복 후 Word | 1 → 1 | **0%** | 99.9905% | 17 |
| 원본 Word → 한글 재저장 후 복원한 Word | 1 → 1 | **0%** | 99.9905% | 17 |
| 첫 번째 HWPX → 세 번째 HWPX, 한글 출력끼리 | 1 → 1 | **0%** | 100% | 0 |

변경 비율은 RGB 채널 차이 **24 초과**, 표시 영역은 어느 한쪽이라도 RGB 최솟값이
245 미만인 픽셀의 합집합을 기준으로 계산했습니다. Word 두 경로는 작은 색상 차이가
남으므로 임계값 적용 전의 픽셀 배열은 동일하지 않습니다. 한글 출력끼리는 임계값 적용
전에도 픽셀 배열이 같습니다. Word PDF의 읽기 순서로 추출한 텍스트는 일치합니다.
원시 PDF 글자 객체의 순서는 달라질 수 있어 객체 배열의 직접 비교를 텍스트 동일성으로
사용하지 않았습니다. 이 결과는 해당 샘플에 한정됩니다.

한글의 PDF 높이는 790pt, Word는 792pt였습니다. 위 표의 Word 비교는 모두 Word끼리,
한글 비교는 한글끼리 수행했습니다. Word와 한글 화면이 서로 같다는 측정 결과가 아닙니다.

한글 자동 갱신은 구조 검사와 별도로 실제 한글에서 다음과 같이 확인했습니다.

| 기능 | 조작 | 결과 |
| --- | --- | --- |
| 자동 목록 | 마지막 항목에서 Enter 후 새 항목 입력 | 3번 항목 생성; DOCX의 같은 자동 목록으로 복원 |
| 날짜·문서 요약 정보 | 오래된 표시값을 가진 HWPX 열기·저장 | 현재 날짜 및 문서 제목·주제로 갱신 |
| 범위 책갈피의 `REF`, `PAGEREF` | 원문 범위의 글자 수정 후 저장 | 참조 내용과 쪽 번호 갱신; Word 명령 복원 |
| `PAGE \* roman`, `NUMPAGES` | 2페이지 HWPX 열기·PDF 출력 | `i / 2`, `ii / 2` 출력 |
| `= SUM(LEFT) \# "#,##0.00"` | 표의 `10`, `20` 중 첫 셀을 키보드로 `15`로 수정 | 즉시 `35.00` 표시; 저장 후 DOCX에서도 입력·결과·명령 유지 |

계산식은 한글 오토메이션 `InsertText`로 같은 값을 수정했을 때 재계산되지 않았습니다.
한글이 직접 작성한 계산식에서도 같은 차이가 있었으며, 키보드 입력 경로에서 동작함을
확인했습니다. 따라서 자동화 API의 저장 성공만으로 재계산 성공을 판정하지 않습니다.

한글은 서로 다른 필드에 같은 `fieldid`를 저장할 수 있습니다. 검증기는 고유한
`fieldBegin/@id`와 `fieldEnd/@beginIDRef`의 연결, 각 쌍의 `fieldid` 일치를 검사하도록
수정했습니다. 정상적인 한글 재저장 파일을 중복 `fieldid` 때문에 거부하지 않습니다.
또한 한글 상호 참조의 `RefPath=?책갈피;`에서 실제 대상 이름을 읽어 검증합니다.

지원하는 범위와 남은 근사는 [DOCX addon 안내](./docx-addon.md#한글에서-자동-갱신되는-목록과-필드)를
참고하세요. 모든 Word 날짜·조건·목차 필드나 번호 형식이 한글 자동 기능으로 매핑되는
것은 아니며, HWP 바이너리 출력의 제한도 별도로 남아 있습니다.

## 추가 손실 4건 수정 후 검증 (2026-10-29)

정상 Word 문서에 번호 정의가 없을 때의 열기 실패, 중첩 필드의 내부 값·명령 유실,
여러 문단에 걸친 목차 필드의 명령 유실, Word 텍스트 상자 글자 유실을 재현하고
수정했습니다. 번호 정의가 없는 원본의 무수정 DOCX 바이트 보존, 중첩 필드 명령 안의
내부 필드, 본문·머리말·표 셀 각각에서 여러 문단에 걸친 필드 범위, 텍스트 상자의 대체 표현 중복
방지와 문단 서식·링크·그림·표·필드의 3회 왕복을 회귀 검사에 추가했습니다.

복합 필드의 결과는 한글 문서 안에 편집 가능한 내용으로 둡니다. Word 명령과
시작·끝 속성을 별도로 보존하므로 변경된 결과를 DOCX로 복원할 수 있습니다.
이는 한글에서 `IF`나 `TOC` 자체를 계산한다는 뜻은 아니며, 해당 바깥 필드에는
자동 갱신을 지원하지 않는다는 경고를 냅니다.

실제 Word에서 새로 만든 1페이지 텍스트 상자 샘플을 HWPX로 변환하고, 실제 한글에서
재저장한 뒤 DOCX로 복원했습니다. Word 출력끼리 144 DPI로 비교한 결과는 다음과 같습니다.

| 항목 | 결과 |
| --- | --- |
| 본문 및 상자 안 글자 | 유지; 대체 표현에 의한 중복 없음 |
| 한글 기본 글상자 수 | 1개 |
| 원본 Word와 복원 Word 페이지 수 | 1 → 1 |
| 흰 배경 제외 변경 픽셀 | 0 |
| 표시 영역 IoU | 100% |
| 최대 RGB 채널 차이 | 0 |
| 임계값 적용 전 픽셀 배열 | 동일 |

수정 도중 상자 글자의 세로 위치가 0.12pt 달라지는 현상도 확인했습니다. 원본 Word의
호환 모드 15가 새 파일의 기본 모드 14로 바뀐 것이 원인이었습니다. 호환 설정을
보존한 후 위 샘플의 픽셀 배열이 일치했습니다. 이 결과는 해당 샘플과 경로의 측정입니다.

텍스트 상자의 글자를 실제 한글에서 바꾼 뒤 DOCX로 복원해 새 글자만 남는 것도
확인했습니다. 형상 템플릿에는 원래 본문을 넣지 않으며, 오래된 내용을 다시 되살리지
않도록 VML 보조 캐시도 제거합니다. 여러 상자가 포함된 그룹 도형과 모든 Word 필드의
한글 내 자동 계산은 이번 수정 범위에 포함되지 않습니다.

## 2026-11-04 Word 세부 편집과 다페이지 검증

`examples/docx_advanced_editing.py`에 병합 표의 행·열 삽입, 한영 혼합, 각주, 선택적 그림,
목록·날짜·쪽 번호 필드, 가로 용지·다단이 있는 회귀 예제를 추가했습니다. 편집본과
DOCX→HWPX→DOCX 복원본을 같은 Microsoft Word에서 PDF로 출력하고, 같은 Poppler
96dpi 설정으로 렌더링했습니다. 페이지 크기를 바꾸거나 이미지를 정렬하지 않고 비교합니다.
이 예제에서 모든 페이지의 픽셀 배열이 일치했으며, 흰 배경 제외 변경률 0%, 잉크 IoU 1.0을
확인했습니다. 비교 스크립트는 `scripts/compare_document_renders.py`입니다.

검증 중 필드만 있는 꼬리말이 빈 영역으로 판정돼 사라지는 문제, 병합 셀의 실제 연속
행에서 테두리가 사라지는 문제, 한글에서 머리글 색이 표 전체로 상속되는 문제를 수정했습니다.
표 전체에 중립 배경 정의를 먼저 배정하고 각 셀의 배경을 별도로 적용합니다.
오른쪽 단까지 글이 흐르는 조건에서는 Word의 기본 widow/orphan 보호가 HWPX 기본값과
달라 문단 중간이 단 경계에서 갈리는 문제도 확인했습니다. Word에서 생략된 기본값을
명시적으로 매핑해 이 페이지·단 나눔 차이를 수정했습니다.

한글에서도 생성한 HWPX의 열기·PDF 출력·재저장을 확인했습니다. 균등 2단 및
비균등 2단(200pt/322pt, 간격 18pt)의 폭과 구분선 설정이 재저장 후 유지됐습니다.
Word와 한글의 직접 렌더링 사이에는 글꼴 배치·행 높이·탭 채움선 차이가 남으며,
위의 픽셀 일치는 Word 편집본과 Word 왕복 복원본 사이의 결과입니다.

## 2026-11-04 객체 endpoint와 고급 수식

`examples/word_endpoint.py`는 범위 편집·책갈피·링크·스타일·표 나누기/합치기와
행렬·합계·적분을 포함합니다. 편집본과 HWPX 왕복 복원본을 Word에서 출력한 1페이지를
같은 Poppler 120dpi로 비교해 전체 픽셀 일치, 흰 배경 제외 변경률 0%, 잉크 IoU 1.0을
확인했습니다. 한글에서도 수식이 이미지가 아닌 편집 가능한 수식 객체로 표시됐습니다.
두 앱의 직접 수식 크기·정렬·문단 배치에는 차이가 남습니다.

Word SaveAs는 알 수 없는 속성과 `paraId`를 다시 만들거나 숨김 책갈피 시작을 문단
밖으로 옮길 수 있었습니다. 숨김 앵커와 ID·해시 기록을 사용해 문단 UUID를 복구하고,
실제 Word 재저장 뒤 같은 UUID로 편집된 문단을 다시 조회했습니다. 현재 endpoint는
링크 대상·표시값의 해시와 문단 앵커를 함께 기록해 `w:hyperlink`와 리터럴 `HYPERLINK`
필드 사이의 유일한 대응도 같은 논리 ID로 연결합니다. 중복 링크는 추측해 연결하지 않습니다.
현재 메타데이터로 갱신한 예제를 실제 Word SaveAs로 재저장해 기존 33개 객체 ID 전부를
복구했습니다. 필드로 바뀐 링크도 기존 UUID로 `set_text`를 적용했습니다.

수식 속성 보존이 연산자·괄호·제한 표시 여부를 옛 값으로 덮어쓰지 않도록 분리했습니다.
한글에서 합을 적분으로 바꾸거나 괄호를 수정하면 새 의미를 유지하고, 구조가 같은 수식의
글자·제한 위치 같은 표현 속성만 재적용합니다.

## 2026-11-04 모듈 기능 확장 검증

`examples/docx_module_extensions.py`는 cases·왼쪽 쌓기·조합·무선 분수·괄호 행렬,
여러 문단과 표를 가진 복합 필드 결과, 콘텐츠 컨트롤, 파트 간 이동과 명시적 필드 갱신을
생성합니다. 단위 검사에는 오른쪽 쌓기·eqalign·열별 행렬 정렬·일반 상하한·다중 인수
구분 괄호의 현재 피연산자 복원도 포함합니다. Word의 세로 정렬 속성 `baseJc`에
가로 정렬 값을 넣지 않고, 왼쪽/오른쪽 쌓기는 열 정렬이 있는 OMML 행렬로 작성합니다.

실제 Word에서 숫자 IF, 문자열 IF, 와일드카드 IF를 갱신해 모듈 결과와 비교했습니다.
문자열 대소문자를 구분하며 `IF 2 < 10`은 숫자로 비교합니다. 복합 결과와 목차의
보존 화면을 비교할 때는 필드를 잠가 Word의 자동 재계산을 막았습니다. 잠기지 않은
필드는 Word가 열기·재계산 중 결과와 서식을 다시 만들 수 있습니다.

새 예제의 Word 편집본과 HWPX 왕복 복원본은 모두 1페이지이며, PDF에서 추출한

독립된 두 본문은 총 **25쪽·수식 675개**입니다. `기출킬러양식_spacing_fix.hwpx` 분리본도
추가로 확인했지만 첫 사례와 본문이 같아 독립 표본 수에 포함하지 않았습니다.
두 본문의 공통 모델 직접 저장 경로도 픽셀 일치를 확인했습니다. 기존 Word 시작 문서
세 종의 8쪽도 다시 비교해 전체 픽셀 일치를 유지했습니다.

같은 `spacing_fix` 분리 기준본에 수정 전 수식 코덱과 기준선 처리 방식을 재현한 대조군은
배경 제외 변경률이 **46.238%**였고 수정 후에는 0%였습니다. 앞 표의 전체 문서 65.117%와는
제외 범위가 다르므로 이 둘을 같은 기준의 개선율로 해석하면 안 됩니다. 모든 비교는 같은
한글에서 PDF를 출력하고 Poppler 120dpi에서 정렬·크기 조절 없이 수행했습니다. 잉크 합집합의
변경률 0%뿐 아니라 문자 좌표와 전체 RGB 픽셀도 일치합니다.

이번 수정은 다음 원인을 해결합니다.

- 원본 수식의 `baseLine`과 호스트 run 글자 서식을 보존합니다. 원본에 없던 기준선 속성을
  임의로 넣지 않으며, 수식의 피연산자·첨자 구조를 편집하면 옛 크기·기준선을 버립니다.
- `v left`, `15 sqrt`, 함수명 등의 토큰 경계를 유지하고, bar·accent·글꼴·관계 기호·함수·
  수식 공백을 실제 Word OMML 구조와 속성으로 변환합니다. 명령어를 보이는 글자로 넣지 않습니다.
- 합 기호의 피합산식에 속하는 첨자·분수를 연산자 바깥으로 옮기지 않습니다.
  `sqrt {차수} of {식}`도 처리하며, 글꼴 초기화로 분리된 첨자와 일반 동시 첨자를 구분합니다.
- `cases`와 단일 열 `eqalign`의 조판을 보존하고, Roman 글자 뒤의 기울임꼴 복귀 명령을
  반복하거나 연산자 앞으로 옮겨 수식 간격을 바꾸지 않습니다.
- 인라인 표 뒤에서 수식으로 시작하는 문단에도 원래 문단 위치와 서식을 연결합니다.
  522개 수식 표본에서 표 뒤 수식 다섯 개가 문서 끝으로 이동하던 문제를 수정했습니다.
- 본문의 고정폭 공백 `hp:fwSpace`와 줄바꿈 방지 공백 `hp:nbSpace`를 구분하여 보존합니다.
  고정폭 공백 누락으로 큰 제목이 가로로 이동하던 문제와 편집 시 공백 종류가 사라지는 문제를
  수정했습니다. Word 공통 모델에서는 각각 U+2007과 U+00A0으로 다룹니다.

수식을 그림으로 대체하거나 원래 수식 피연산자를 따로 저장해 덮어쓰지 않습니다.
이 결과는 **분리한 본문의 왕복 검증**이며, 제외한 도형·자동 번호·그림·쪽 장식이나
DOCX 중간 파일의 Word 화면과 원본 한글 화면의 동일성까지 검증했다는 뜻은 아닙니다.
한글 앱의 재저장이 addon 파트를 제거하는 경계도 위 설명과 같습니다.

재현 방법:

```sh
python scripts/validate_hwpx_math_body.py examples/samples/hwpx/spacing_fix.hwpx --output-dir build/math-body
# 같은 한글에서 body-source.hwpx, returned.hwpx를 각각 PDF로 출력한 뒤:
python scripts/compare_document_pdfs.py build/math-body/body-source.pdf build/math-body/returned.pdf --output-dir build/math-body/comparison
```

`structure.json`은 문단·수식 수, 본문 순서, 수식 계층·피연산자·의미 속성을 확인합니다.
구조 검사의 통과만으로 배치가 같다고 판정하지 않으며 PDF의 모든 페이지도 비교해야 합니다.
검증 도구의 비교 의존성은 위와 같습니다. 로컬 실측 자료는
`build/math-body-qa/{spacing,template}/structure.json`과 각 `comparison-returned/comparison.json`에
있습니다. 수식 명령은 [한컴 수식 형식 revision 1.3](https://cdn.hancom.com/link/docs/%ED%95%9C%EA%B8%80%EB%AC%B8%EC%84%9C%ED%8C%8C%EC%9D%BC%ED%98%95%EC%8B%9D_%EC%88%98%EC%8B%9D_revision1.3.pdf)을 참고했습니다.

최종 DOCX/Word·한글 공통 문서·렌더 비교 회귀 검사는 **375개 통과, 4개 건너뜀**입니다.
건너뛴 검사는 위와 같은 미포함 수학 샘플입니다. 본문 저수준 편집 검사도 별도로 통과했으며,
Ruff, 설정된 85개 파일의 mypy, 수식·native 속성 모듈의 함수 본문 타입 검사와
빌드한 wheel의 양방향 변환·기준선·공백·피합산식 구조 검사도 통과했습니다.
